# Decisions

Agreed design decisions, and items deliberately deferred to later milestones.
Changing a recorded decision needs discussion first (`CLAUDE.md`).

## Milestone 4 — Jira integration

Approved before implementation, including the five amendments marked *(amended)*.

| # | Decision | Rationale |
|---|---|---|
| D4.1 | Three layers: `TicketService` interface → `JiraTicketService` → `JiraClient` (httpx, REST v3) + `TicketStore` (SQLite). | The graph (M5) depends only on the interface; Jira and SQLite can be faked in tests. |
| D4.2 | Email lives in the issue description (`Employee email: …`) and as a label `sd-emp-<sha256(email)[:16]>`. No custom field. | Project KAN is team-managed; custom fields need admin UI setup. Labels support exact JQL lookup. |
| D4.3 | The `sd-emp-` hash is unsalted and documented as **pseudonymisation, not anonymisation**: it is reversible by dictionary attack. *(amended)* | Same email gives the same label on any machine, with no shared secret. The plain email is in the description anyway. |
| D4.4 | Lookup = Jira label search ∪ SQLite `employee_tickets` mapping, with write-back. Jira is the source of truth for status and comments. Ownership is required for `get_ticket`. | The spec asks for a local mapping (Q13). SQLite also covers Jira's search-index lag. |
| D4.5 | Op id = `sha256("smartdesk-op-v1" + session_id + canonical draft)`, carried as label `sd-op-<op_id[:32]>`. | Same approved draft in the same session gives one ticket. An edited draft or a new session gives a new one. |
| D4.6 | `ticket_ops` states: `pending`, `unknown`, `created`, `failed`. A connect error or 4xx means `failed` (safe to retry). A read timeout, dropped connection or 5xx means `unknown`. | Separates "definitely not created" from "may exist". |
| D4.7 | An `unknown` op is always reconciled (label search, 3 polls × 2 s) before any further POST. At most `JIRA_MAX_CREATE_ATTEMPTS` (2) POSTs per call. If several issues match, the oldest wins. | "Reconcile before retrying; never blindly repeat creation." |
| D4.8 | Reads retry with exponential backoff on timeouts, 429 and 5xx, and **honour `Retry-After` on 429**, capped at 30 s. Creation is never retried by the transport. *(amended)* | Reads are idempotent; creation is not. |
| D4.9 | `jira_live` tests need **both** the `JIRA_*` credentials **and** `SMARTDESK_LIVE_TESTS=1`. *(amended)* | Credentials are configured locally, so a plain `pytest` would otherwise create real tickets. |
| D4.10 | Live-test teardown deletes the issue. **If the delete fails, it moves the issue to Done and keeps the `sd-live-test` label.** *(amended)* | Leaves no open test tickets, and leftovers stay findable. |
| D4.11 | Demo and test tickets are created **only via SmartDesk or `python -m smartdesk.tickets`**. The human agent only updates them in the Jira UI (`docs/demo-script.md`). *(amended)* | Tickets made in the Jira UI lack the `sd-emp-` label and would be invisible to status lookups. |

## Milestone 5 — Orchestration and HITL

Approved before implementation, including the four amendments marked *(amended)*.

| # | Decision | Rationale |
|---|---|---|
| D5.1 | Single agent with deterministic routing. New intents: `provide_info`, `cancel`, `unclear`. The classifier gets a second system message describing the flow state (what SmartDesk is waiting for, a draft on hold, a ticket just offered). Plain answers (an email when asked, a list number when choosing) skip the LLM. | Lets "yes please", "it's jane@…" and "2" be told apart from new requests without a multi-agent design. |
| D5.2 | Ticket slot-filling: one structured LLM call returns the complete updated draft. Ask order: description → email → category (only if unknown). The summary is derived, never asked. Priority is inferred or set at review, never asked. Every field goes through `TicketDraft`'s validators; invalid values are dropped (an over-long summary falls back to one derived from the description). | FR-4.2: mandatory fields collected, category inferred, description summarises the conversation. |
| D5.3 | `present_ticket` adds the full summary to the history, then `review_ticket` calls `interrupt()` with `{op_id, draft, text}`. Resume values: `approve(op_id)`, `edit(fields)`, `cancel`, `message(text)`. Approval is bound to `op_id = derive_op_id(thread_id, draft)`: an edit changes it, so a stale approval is rejected. `submit_ticket` re-checks `approved_op_id` before calling Jira and is the only node that creates tickets. | FR-4.3: no ticket without explicit approval of its final details. |
| D5.4 | After any Jira error the draft is kept and "try again" goes back through review (approval asked again). Unchanged draft → same op_id → M4 reconciliation prevents a duplicate. | Never reuse an approval across a failure; never blindly repeat creation. |
| D5.5 | Create-path messages: `JiraUnavailable` / `JiraAuthError` / `JiraRequestRejected` say the ticket was **NOT created** and the draft is saved; **only `TicketCreationUncertain`** says it may exist and that a retry checks first. To make that true, `JiraTicketService._reconcile` turns any `JiraError` from its search into `TicketCreationUncertain`. *(amended)* | A failed reconcile search happens when a POST may have succeeded; "not created" would be false there. |
| D5.6 | Session email capture only when SmartDesk asked for it (`awaiting == "email"`), when the message is essentially just an address, or after an explicit "my email is …". Other addresses are ticket content and never lock or conflict. Once set, the email is locked; a different one routes to `email_locked`. Lookups always use the locked email. *(amended)* | A colleague's address in a description must not hijack or block the session. |
| D5.7 | The email is a demo identifier, not authentication (README). | Spec §10 Q19; a real deployment would use SSO. |
| D5.8 | `SqliteSaver` (`langgraph-checkpoint-sqlite`) on the same `data/smartdesk.db` as the ticket tables, WAL mode. `thread_id` = session id; the CLI prints it and resumes with `--session`. History, email lock, drafts and a pending approval survive a restart. | NFR-2.1; spec Q16. |
| D5.9 | `graph.session.ChatSession` is the **only** entry point for application code (CLI now, Chainlit in M8). It maps typed text at an approval to approve/cancel only for exact words, else `message`. M8 can switch to `AsyncSqliteSaver` or run the sync graph in a worker thread by changing `ChatSession` and the checkpointer factory, without touching nodes. *(amended)* | Keeps interrupt/resume mechanics and the execution model in one place. |
| D5.10 | `data/smartdesk.db` stores full conversations and employee emails locally (git-ignored); the README says how to delete it. *(amended)* | Personal data at rest must be visible to the operator. |
| D5.11 | A question asked mid-flow is answered normally; a ticket draft is kept "on hold" with a reminder, and "continue my ticket" resumes it. Status candidates are cleared by any intent other than `provide_info` / `ticket_status`. | NFR-2.2: intent changes without losing the topic. |
| D5.12 | Message history is not trimmed or summarised in M5. | Fine for demo-length sessions; revisit if traces show token growth. |
| D5.13 | **Bug found in live testing:** after KAN-6 (monitor) was created, "I need a new laptop, my manager bob@test.com approved it" produced the draft "Monitor Flickering Issue and Laptop Request". **Root cause:** the ticket extractor saw session-wide history (the last 20 messages), so it summarised the earlier ticket's conversation too; nothing recorded where a ticket began. **Fix 1:** `ticket_flow_start` records the message index where the current ticket began; with no ticket in progress, `create_ticket` starts an empty draft, and the extractor only sees messages from that index. A ticket accepting an escalation offer starts at the escalated question (`seed_start`, see Fix 3). The index is kept while a draft is on hold or after a Jira error, and cleared on creation or cancel. **Fix 2:** a `create_ticket` request while a draft is on hold asks "You have a ticket draft on hold about '…'. Continue that one, or start a new ticket?" Exact phrases are matched first, like approve/cancel: "continue" resumes the held draft unchanged (same op_id); "new" discards it and extracts from the request that triggered the question (or from its `seed_start`). Other replies go to the classifier: still an answer → asked again; something else → handled normally, draft kept on hold. A request that is itself a continue phrase ("continue my ticket", "try again") resumes without asking. **Fix 3 (also found in live testing):** after a KB answer about VPN, "I want to raise a ticket for it" asked for a description from scratch, because the flow started at the request and "it" was lost. Now both `generate_answer` (grounded) and `escalate` set `seed_start` to the index of the question they handled; `classify_intent` keeps it only when the very next turn is `create_ticket`, and the new flow starts there. Living one turn, and set only by KB turns, it can never reach back past a created or cancelled ticket. **Limitation:** the extractor now also sees the preceding question when the request is unrelated ("How many sick leave days…?" → "I need a new laptop"). Keeping that question out of the draft relies on an LLM prompt rule (use it only if the request refers back to it), not on code; covered by live tests and to be measured over the eval set in M7 (M7-1). | Each ticket must contain only its own conversation (FR-4.2 "summarise the conversation" means this ticket's), an on-hold draft must not silently absorb or be replaced by a new request, and "a ticket for it" must carry the topic just discussed. Regression tests: `test_new_ticket_after_a_created_one_starts_from_a_fresh_draft`, `test_escalated_question_seeds_the_new_flow_but_earlier_turns_do_not`, `test_new_discards_the_held_draft_and_starts_from_the_request`, `test_continue_resumes_the_held_draft`, `test_ticket_for_it_after_a_kb_answer_starts_from_that_question`, `test_kb_question_never_seeds_a_ticket_past_a_closed_ticket_or_another_turn`, `test_draft_on_hold_then_kb_question_then_new_ticket_excludes_the_held_draft`; live: `test_live_ticket_for_it_uses_the_question_just_asked`, `test_live_unrelated_ticket_ignores_the_question_just_asked`, `test_live_new_ticket_after_held_draft_and_kb_answer_contains_neither`. |

## Milestone 6 — Guardrails and reliability

Approved plan: `docs/specs/m6-plan.md`.

| # | Decision | Rationale |
|---|---|---|
| D6.1 | **M6-1 resolved with a lease.** `ticket_ops` gains a `version` column that every write bumps. `take_over(observed)` moves an `unknown` (or stale `pending`) op to `pending` only if its status *and* version are unchanged (`UPDATE … WHERE status=? AND version=?`, `rowcount == 1`). The owner renews the lease (`heartbeat`, compare-and-set on its version) before every POST and every reconcile poll. A caller whose renewal fails has lost the op: it raises `TicketCreationUncertain` **without posting**, and its give-up `mark_unknown` is conditional on its version, so it cannot overwrite the new owner's `created`. Op ids must be 64 hex characters. **Refinement of the M6-1 to-do:** a version counter rather than `attempts` as the compare value, because a heartbeat must invalidate an older owner even when no POST was counted. | Exactly one caller may POST for an op at any time; reconcile-then-retry (D4.7) is unchanged. Tests: `tests/test_tickets_concurrency.py` (in-flight caller during a takeover → 1 POST; stale takeover where the old owner loses the lease and its give-up does not overwrite `created`; outdated takeover refused; schema migration). |
| D6.2 | **Stale-pending timing.** A `pending` op is in flight for `in_flight_seconds = 2 × JIRA_TIMEOUT_SECONDS` (20 s by default) after its last heartbeat; after that another caller may take it over. Heartbeats come right before each POST and each reconcile poll. **During a POST** the gap is one create request, which is never retried by the transport and has a 10 s timeout, so it stays under 20 s. **During a reconcile search** the gap can exceed 20 s (reads retry with backoff and honour `Retry-After` up to 30 s); a takeover there is harmless, because the old owner only searches and checks its lease before any POST. **Residual risk:** if one POST outlasts the window (httpx applies the 10 s per phase, so connect + write + read could in theory exceed 20 s) *and* its issue is not yet searchable when the new owner reconciles, two issues can be created. Both carry the op label and `_reconcile` keeps the oldest. | Bounded by configuration and documented rather than eliminated; eliminating it needs a lock held across the HTTP call, which SQLite and Jira do not offer together. Listed in `docs/known-issues.md`. |
| D6.3 | **LLM retries and fallback.** Every request has `SMARTDESK_LLM_TIMEOUT_SECONDS` (30 s) and `SMARTDESK_LLM_MAX_RETRIES` (2): the OpenAI client retries connection errors, timeouts, 429 and 5xx with exponential backoff and jitter, honouring `Retry-After`. After that, `ResilientChatModel` sends the same structured call to `SMARTDESK_LLM_FALLBACK_MODEL` for service and output-parsing errors only (`FALLBACK_ERRORS`); a 400 or a bug in SmartDesk is not masked. **`gpt-4.1-mini` returned 403 (PermissionDenied) on the IK key.** A structured-output probe showed `gpt-4o-mini`, `gpt-4o` and `gpt-5` available; **`gpt-4o` was approved as the fallback** and is the documented value in `.env.example` (same family as the primary, accepts temperature 0). The code default stays blank, which means a canned reply (D6.4); that reply also follows when the fallback fails too. Ticket creation keeps the M4 reconcile-then-retry and is not retried by this layer. | NFR-3.2. A second model only where it can help; no unverified model in the default config. Tests: `tests/test_m6_reliability.py` (real `ChatOpenAI` over a mocked transport: 500 → 3 requests then fallback, 429 retried, 400 neither retried nor sent to the fallback, both failing → canned reply). |
| D6.4 | **Graceful turn failures.** `ChatSession._run` catches any exception from a turn, logs only its type and a session-id prefix, and replies `LLM_UNAVAILABLE` (for `FALLBACK_ERRORS`) or `INTERNAL_ERROR`, adding "Your ticket draft is saved." when there is one. `TurnResult.error` reports `llm_unavailable` / `internal_error`. The next turn starts normally. **Deviation from the plan's wording** ("a pending approval survives a failed turn"): when the failure happens while handling a reply *at review*, that resume value is already consumed, so the approval is no longer pending. The draft survives; the next message shows it for review again with the same op_id, and only a fresh approval creates the ticket. | Safe by construction: approval is never carried across a failure (same principle as D5.4). Test: `test_failure_while_handling_a_review_reply_never_creates_a_ticket`. |
| D6.5 | **Input guardrails** (`smartdesk.guardrails`, applied in `ChatSession.send`): NFKC normalisation; control, zero-width, bidi and BOM characters removed; empty input and input over `SMARTDESK_MAX_INPUT_CHARS` (2000, measured after cleaning) rejected with a reply. Rejected input is never truncated, sent to the LLM or stored, and a pending approval stays pending. | NFR-1.2 and prompt-injection resistance: hidden characters cannot hide instructions from a human reader, and full-width look-alikes cannot dodge the email lock. Tests: `tests/test_guardrails.py`. |
| D6.6 | **Router history cap.** The intent router sees only the last `SMARTDESK_ROUTER_HISTORY_TURNS` (4) employee turns and the replies between them, plus the flow-state line. **Stored messages are never trimmed**: `ticket_flow_start`, `seed_start` and `pending_flow_start` are absolute message indexes. This narrows D5.12: history is still kept in full, but it is no longer sent in full. | Router cost per turn stays flat over long sessions. Tests: `test_router_gets_only_the_last_turns_but_state_keeps_all_messages`, `test_router_with_one_turn_still_gets_the_flow_state_line`. |
| D6.7 | **Retrieved chunk text is dropped from state** once the answer step is done (answered, ungrounded or low-similarity): only `chunk_id`, `doc_id` and `similarity` are kept. | Checkpoints store the full state at every step, so up to `SMARTDESK_RAG_TOP_K` passages stayed in the turn's remaining checkpoints, including the one the session rests on until the next message, although nothing reads them after the answer. Test: `test_state_keeps_only_ids_and_similarity_of_retrieved_chunks` (the newest checkpoint contains no passage text). |
| D6.8 | **Session maintenance:** `python -m smartdesk.sessions list | delete --session ID | delete --older-than 30d | compact`. It touches **only** LangGraph's `checkpoints` and `writes` tables; `employee_tickets`, `ticket_ops` and Jira are never touched. `compact` keeps each session's newest checkpoint and its pending writes (enough to resume, including a paused approval), then runs `wal_checkpoint(TRUNCATE)` and `VACUUM`. It relies on uuid6 checkpoint ids being time-ordered (as `SqliteSaver` does) and on LangGraph's private `__interrupt__` channel name, which a test checks against a real paused session. `delete` and `compact` ask for confirmation unless `--yes`. | Checkpoint growth is quadratic in session length (measured: 42 checkpoints, ~310 KB for 10 turns). Tests: `tests/test_sessions.py`, including `test_tickets_remain_listable_after_delete_older_than`. |
| D6.9 | **Tool-argument validation** before any Jira call: email through `normalize_email` (strict regex, ≤ 254 chars); ticket keys must match `^[A-Z][A-Z0-9_]*-[1-9][0-9]*$`, carry the project prefix and be ≤ 32 characters; op ids must be 64 hex characters. JQL is built only from the configured project key and SmartDesk's own hashed labels, never from employee text. | A JQL-like key or a quoted email never reaches Jira. Tests: `test_malformed_or_foreign_ticket_keys_never_reach_jira`, `test_invalid_emails_never_reach_jira`, `test_malformed_op_id_is_refused_before_anything_is_recorded`. |
| D6.10 | **Secrets and personal data.** Secrets are `SecretStr` (hidden in reprs). Langfuse traces go through `langfuse_mask` (verified with the real Langfuse client and an in-memory span exporter). A `RedactingFilter` redacts the formatted message and exception text of every log record on the handlers it is attached to; the CLI attaches it to the root handlers. Turn failures log only the exception type. | NFR-3.3 and spec-level privacy: Jira error bodies can echo emails or tokens. Tests: `test_settings_repr_hides_secrets`, `test_log_records_are_redacted`, `test_no_email_or_token_is_logged_during_a_ticket_run_with_a_jira_rejection`, `test_langfuse_traces_are_masked_before_export`. |
| D6.11 | **Prompt injection.** Employee messages and KB passages are data: every prompt says so; delimiter look-alikes are stripped from passages and from the extractor's `<message>`/`<conversation>` blocks; answer citations are validated against the passages actually given (an invented passage number is refused); approval never comes from LLM output, only from exact words in `ChatSession` or a structured resume carrying the shown op_id. | Retrieved documents are untrusted (CLAUDE.md M6). Offline tests in `tests/test_guardrails.py`; live: `test_live_request_for_the_system_prompt_gets_no_prompt_text`, `test_live_instructions_inside_a_kb_passage_are_not_followed`. |
| D6.12 | **K18 fix (amends D5.13 Fix 2).** When "continue or new?" is first asked, `pending_request_index` records the request that triggered it. While the question is open (asked in the previous turn), any reply that is not continue/new, including one the router reads as another ticket request, re-asks and keeps that index; "new" extracts up to and including the recorded request. `classify_intent` clears the index once the question is no longer open. Trade-off: if the employee sends a different request instead of answering, "new" still starts from the first one; they can correct the draft before review. | Found in live testing: "I need a new laptop" → "yes please" → "new" built the ticket from "yes please". Tests: `test_new_after_the_held_draft_question_was_asked_again_starts_from_the_original_request` (both routings), live `test_live_new_ticket_after_held_draft_and_kb_answer_contains_neither` (passed 3/3). |
| D6.13 | **K2 fix.** A draft never keeps a summary while it has no description: `_merge_extraction` drops it, and the extractor prompt asks for an empty summary until the issue is described. Because a just-started ticket now has an empty draft, the router's "ticket draft in progress" line is shown whenever a ticket flow has started (`ticket_flow_start` set), not only when the draft has fields; without it, live routing read the issue description as a new `create_ticket`. | A bare "I'd like to raise a ticket" produced the title "Support ticket request", which the "keep the current title" rule then preserved. Tests: `test_no_title_is_kept_before_the_issue_is_described`, `test_router_is_told_a_ticket_is_in_progress_before_any_field_is_known`, live `test_live_flow_aware_routing` (3/3); live trace now gives "External monitor flickering issue when docked". |

## Resolved in Milestone 6

### M6-1: Compare-and-set before retrying an `unknown` op — resolved by D6.1

The original gap and to-do are kept below for reference.

**Gap.** `create_ticket` guards a *recent* `pending` op as in flight, but an
op in `unknown` has no owner. Two concurrent calls for the same `unknown` op
can both reconcile, both find nothing, and both POST, which creates duplicates.
`record_attempt` updates the row unconditionally, so it does not stop the
second caller. The window is small: it needs a double submit at the same
moment as an ambiguous timeout. It matters once a UI such as Chainlit can run
concurrent turns.

**To do:**
- Add a conditional transition to `TicketStore`, e.g.
  `begin_retry(op_id, expected_attempts) -> bool`:
  `UPDATE ticket_ops SET status='pending', attempts=attempts+1, updated_at=? WHERE op_id=? AND status='unknown' AND attempts=?`.
  It succeeds only when `rowcount == 1`.
- In `JiraTicketService.create_ticket`, use it in place of `record_attempt`
  for every POST that follows a reconcile. If the update matches no row,
  another caller owns the retry: treat it as in flight and raise
  `TicketCreationUncertain`, without posting.
- Apply the same compare-and-set to the reconcile step's start, so a
  `pending` op older than the in-flight window is taken over by exactly one caller.
- Tests: two service instances on one SQLite file interleave on the same
  `unknown` op, and exactly one POST is sent. Also cover a stale `pending`
  op taken over by one of two callers.

## Deferred to Milestone 7

### M7-1: An unrelated earlier question must not merge into a new ticket

**Gap.** A ticket requested right after a knowledge question starts from that
question (`seed_start`, D5.13 Fix 3), so "raise a ticket for it" works. When
the request is unrelated ("How many sick leave days do I get?" then "I need a
new laptop"), keeping the question out of the draft relies only on the
extractor prompt rule. The live tests check three such conversations; that is
not a measurement.

**To do:**
- Add labelled multi-turn cases to `data/eval/` (kept out of the index):
  a preceding question (answered and escalated variants, IT and HR) followed
  by a ticket request that is either **unrelated** (expected: the draft
  contains nothing from the question) or **related** ("for it", "that
  problem"; expected: the draft carries the question's topic). Include the
  held-draft path (draft on hold → question → new request → "new").
- Run them through `ChatSession` with the real LLM and a fake ticket service
  (never real Jira); judge each draft against the labelled topic keywords.
- Report in `docs/evaluation-report.md`: the **no-merge rate** on unrelated
  pairs and the **carry-over rate** on related pairs, with any failures listed.
  If the no-merge rate is not acceptable, consider replacing the prompt rule
  with a classifier field ("does the request refer to the previous turn?")
  that decides the flow start in code.
